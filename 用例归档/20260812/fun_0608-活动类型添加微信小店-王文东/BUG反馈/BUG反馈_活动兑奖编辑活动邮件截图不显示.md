# BUG 反馈：活动兑奖-编辑活动时「邮件截图」不显示

## 基本信息

| 项 | 内容 |
|---|---|
| Bug 标题 | 编辑活动时「邮件截图」缩略图加载失败不显示（部分活动 OSS 地址双编码 404） |
| 所属产品/模块 | 华硕小二 / 管理后台 / 兑换活动管理-活动兑奖 |
| 缺陷类型 | 数据/存储缺陷（上传路径双编码）导致前端展示失败 |
| 优先级 / 严重程度 | P2 / 中（审核凭证无法核对，但不影响列表与创建） |
| 发现人 / 日期 | 王文东 / 2026-08-12 |
| 环境 | https://dev-asus.njsyue.com（测试环境），账号 19552261935 |

## 复现步骤

1. 登录华硕小二后台，进入【兑换活动管理】→【活动兑奖】列表。
2. 点击活动 **wmw抽奖实物20250925002**（编码 0N31，ID 147，审核通过）的【编辑】。
3. 观察「邮件截图」区域是否显示图片缩略图。
4. 抓取 `cms/prize/detail` 接口，查看 `mailImg` 字段值。
5. 浏览器/工具直接访问 `mailImg` 的图片 URL，查看 HTTP 状态。

## 实际结果

- 「邮件截图」区域缩略图**加载失败**（img 元素 naturalWidth=0、complete=true），显示异常占位，无法看到邮件截图内容。
- `detail` 接口返回的 `mailImg` 为**双编码路径**：
  `https://acc-store-04.oss-cn-shanghai.aliyuncs.com/%2Fdev%2Ffile%2Fdflt%2Fsz%2Fnb%2FCE78490AADDE8D22F424FB2D3CD82B63.png?x-oss-...`
- 直接访问该 URL：**HTTP 404**（application/xml）。
- 对照活动（URL 正常 `dev/file/...`）均返回 **HTTP 200**：待审核 139（2 张，image/png）、未通过 118（image/jpeg）、通过 132（3 张）、通过 119（image/jpeg）——缩略图正常显示。

## 预期结果

- 编辑页「邮件截图」应显示已上传的截图缩略图，可放大核对，最多 9 张。
- `detail` 返回的图片 URL 应可直接访问（HTTP 200）且为图片类型。

## 根因分析（推断）

部分活动（146、147，2025-09 前后创建的活动转盘）保存时 `mailImg` 存储为**双重编码**的 OSS 路径（`%2Fdev%2Ffile%2F...`），而正常数据为 `dev/file/...`。前端直接以该 URL 作为 img src，OSS 按对象 key 匹配失败返回 404，图片无法加载。属于上传/存储环节的编码问题（可能对已编码 URL 再次执行了 encodeURIComponent），或该批数据经特定创建链路写入。与活动审核状态无关（146/147 为通过，同状态 132/119 正常）。

## 影响范围

- 已确认受影响：活动 146（wmw抽奖实物兑奖20250925）、147（wmw抽奖实物20250925002）。
- 已确认正常：139（待审核）、118（未通过）、132、119（通过）。
- 建议全量扫描活动表 `mail_img` 字段，统计含 `%2F` 双编码前缀的存量数据。

## 修复建议

- 存储侧：上传保存时避免对 URL 路径二次编码；对存量数据做一次清洗（把 `%2Fdev%2Ffile` 还原为 `dev/file`），并校验 OSS 对象真实存在。
- 前端兜底：img 加载失败时给出可点击的原始 URL 下载/预览能力，便于核对审核凭证。

## 「拖拽上传导致」假设的对照实验结论（2026-08-12 补充）

针对「是否因拖拽上传导致」做了受控对照实验（测试环境，未保存活动、未改动任何活动数据）：

1. **点击选择上传**（input[type=file] 选文件）：上传接口 `cms/file/upload` 正常返回，URL 为 `https://acc-store-04.oss-cn-shanghai.aliyuncs.com/dev/file/dflt/ml/0t/744F239CD982F9EC831EF13D0318F839.png?...`——**路径正常，无 `%2F` 双编码**。
2. **拖拽上传**（对上传组件、表单、页面 body 分别派发 dragenter/dragover/drop）：页面中不存在 `.ant-upload-drag` 元素，**当前版本上传组件未开启拖拽功能**，任何目标 drop 后均**未触发上传请求、未产生新图片**。

结论：**当前版本「邮件截图」不支持拖拽上传，且点击上传产生的 URL 正常**；146/147 的双编码 `%2Fdev%2Ffile` 并非当前拖拽/点击上传链路产生，更可能来自 2025-09 前后的旧版上传-保存代码回归，或页面以外入口（接口/脚本/导入）写入的存量数据。建议开发排查 2025-09 前后 `cms/file/upload` 与活动保存链路的变更记录（git 历史）定位。
